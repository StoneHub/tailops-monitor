TailOps Wormhole File Send Upgrade Plan

Created 2026-07-03 for the macOS widget-first TailOps app. Updated after confirming cross-account Taildrop and Taildrive are not the right fit.

Decision

Build Send via Wormhole and Receive via Wormhole controls backed by Magic Wormhole. Taildrop and Taildrive are not suitable for Monroe-to-Ben cross-account sends. SFTP remains a later unattended-drop option, but Wormhole is the simplest no-password path when Ben can click receive.

Current State

  • TailOps still has same-account Taildrop through Finder and row drops.
  • Ben's Mac is visible in Tailscale status, but not in tailscale file cp --targets because Taildrop is personal-device-only.
  • Taildrive shared-machine limitations make it a poor cross-account drop path for this workflow.
  • wormhole is not installed on Monroe's Mac as of this plan update, so runtime UI must show a clear install/setup gate.
  • The widget itself should stay passive; any file picker, receive sheet, or transfer process should run in the host app.

Permission Gates

Gate Impact Required UX
Live participation Magic Wormhole expects both clients to run around the same time and stay running until transfer completion. Show "Waiting for Ben" / "Waiting for Monroe" and allow cancel/retry.
Install dependency Both Macs need the wormhole CLI or a bundled implementation. Detect missing wormhole and show exact install/setup instructions instead of failing silently.
One-time codes Wormhole codes are intended to be one-time. Do not reuse a static PIN for every transfer. Use a one-time setup secret, then derive fresh per-window transfer codes.
Receive folder Ben should control where received files land. Default to ~/Desktop/TailOps Inbox and create it if missing.

Implementation Steps

  1. Done: add core models for paired Wormhole contacts, shared setup secret, inbox path, and widget-to-host open requests.
  2. Done: add deterministic code derivation: setup secret plus pairing ID plus transfer time window produces number-word-word-word-word.
  3. Done: add a host-app Wormhole runner around wormhole send --code <code> <file> and wormhole receive --accept-file <code>.
  4. Done: add a floating Wormhole window with Send and Receive modes.
  5. Done: add widget/AppIntent buttons that only open the host app Wormhole window.
  6. Done: add signed pending-transfer notices over Tailscale so a paired computer card can glow before receive starts.
  7. Add QR setup and cancellation; current setup UI uses shared text fields and a generated setup secret.
  8. Update install verification once the real app includes the Wormhole window.

Packaging Decision

First local trials should require wormhole to be installed separately, usually with brew install magic-wormhole. TailOps should detect the missing executable and show the exact setup step.

Bundling remains feasible because Magic Wormhole is MIT-licensed, but the reference implementation is a Python CLI with native crypto dependencies. Treat bundling as a later packaging task: build per architecture, place the signed helper inside the app bundle, verify notarization, and keep the helper update path explicit.

Widget Behavior

  • Do not run file pickers or Wormhole processes inside the WidgetKit extension.
  • Use OpenTailOpsWormholeIntent to write tailops-open-wormhole.json, post a distributed notification, and open the host app.
  • Keep widget labels short: Send and Receive.

Counterpoint

Wormhole is not unattended. If Monroe needs to drop files while Ben is away, use an SFTP key to a dedicated drop account or a future token-authenticated TailOps Inbox receiver. Those paths are more setup-heavy and should stay separate from the first Wormhole slice.
